# Internationalization

This proposal describes building a site in multiple languages. It draws on Astro, SvelteKit with Paraglide, Next.js with next-intl, Nuxt i18n, and Hugo. The examples use Svelte templates and read their data through `query` from the `shugo` module.

## Decisions

- Internationalization moved to the proposals on November 21, 2026.
- Store translated strings in the project database. A change to a string then reevaluates only the pages that display it. The project author proposed and agreed to this on November 22, 2026.
- Calls to `t` in `.ts` and `.js` modules may use computed keys. The function reports missing keys when it reads the strings table. The project author made this decision on November 22, 2026.

## How other frameworks handle it

| Framework | One page file for every language | String sources | Default-language URL |
| --- | --- | --- | --- |
| Astro | One folder per language | Manually maintained catalogs | No prefix |
| SvelteKit + Paraglide | Yes | `messages/en.json`, one function per string | Configurable |
| Next.js + next-intl | Yes | `messages/en.json` in ICU format | Prefixed |
| Nuxt i18n | Yes | Per-language files in vue-i18n format | No prefix |
| Hugo | One file or folder per language | `i18n/en.toml` with CLDR plural forms | No prefix |

- Four of the five render one template for all languages and use a function to look up strings. Astro uses a separate file for each language and leaves string catalogs to the application.
- URLs usually omit the prefix for the default language and use `/<language>/` for others.
- Each framework does pluralization differently.
- Avoid storing the current language in shared state. A static build has no request to supply it, and one page's language could leak into another.

## Proposal

### Configuration

```json
{
  "site": "https://example.com",
  "data": "data/site.db",
  "i18n": {
    "locales": ["en", "es"],
    "default": "en",
    "prefixDefault": false
  }
}
```

English is at `/about` and Spanish is at `/es/about`. Export writes `about.html` and `es/about.html`. The home pages become `index.html` and `es.html`.

### One page per template, with the locale as an explicit value

Each page file is evaluated once per language. Read the language using `locale` from the `shugo` module. `getStaticPaths` runs separately per language and has access to the same value, so languages can have different paths.

Store localized product text in a separate database table with a locale column.

```svelte
<!-- src/pages/products/[slug].svelte -->
<script module>
  import { query, page, t, locale } from "shugo"

  export function getStaticPaths() {
    return query("product_texts").select("slug", "product").where({ locale }).all()
      .map(({ slug, product }) => ({ params: { slug }, key: product }))
  }
</script>

<script>
  const text = query("product_texts").where({ locale, slug: page.params.slug }).first()
  const product = query("products").get(text.product)
  const date = new Intl.DateTimeFormat(locale, { timeZone: "America/New_York" })
</script>

<svelte:head><title>{text.title}</title></svelte:head>
<h1>{text.title}</h1>
<p>{t("product.inStock", { count: product.stock })}</p>
<time datetime={product.arrival}>{date.format(new Date(product.arrival))}</time>
```

- `key` associates translations of the same page. Shugo uses it to link `/products/pitcher` and `/es/products/jarra`.
- `where({ locale })` is an equality lookup. Changing the Spanish text affects only the pages that read that row.
- A page can specify its available languages in `<script module>` with `export const locales = ["en"]`.

### Strings

A database table holds the key, language, and text of each string. Author one JSON catalog per language and load it through a [data adapter](data-adapter.md) or the project's usual data-loading process.

```jsonc
// locales/en.json
{
  "nav.home": "Home",
  "product.inStock": {
    "one": "{count} item in stock",
    "other": "{count} items in stock"
  }
}
```

- Keys are flat. Placeholders use braces.
- Plural messages are objects keyed by CLDR category. Shugo selects the category from `count` as `Intl.PluralRules` does. English uses `one` and `other`. Keep the count in the string so translators can position it.
- `t("key", { … })` from the `shugo` module reads the current page's language through `query`. The page tracks the rows it reads. The same call works in components.

```svelte
<!-- src/components/Stock.svelte -->
<script>
  import { t } from "shugo"

  let { count } = $props()
</script>

<p>{t("product.inStock", { count })}</p>
```

### Build-time validation

The build fails if:

- The key is missing from the default language.
- Another language's string uses different placeholders.
- A plural message lacks a category required by its language.
- A key in a template is computed instead of written as a string literal.

Shugo detects computed keys in the syntax tree from the Svelte compiler. esbuild handles `.ts` and `.js` modules, where `t` can use computed keys and checks them at lookup time.

If a key is missing in a secondary language, Shugo uses the default-language string and lists the missing keys in the build report.

### Framework features

- `alternates` from the `shugo` module gives the same page's other languages as `[{ locale, url }]`. Use it to build a language switcher.

  ```svelte
  <!-- src/components/LanguageSwitch.svelte -->
  <script>
    import { alternates } from "shugo"
  </script>

  <nav>
    {#each alternates as other}
      <a href={other.url} hreflang={other.locale} lang={other.locale}>{other.locale}</a>
    {/each}
  </nav>
  ```

- `localeUrl("/about", "es")` returns a page's URL in another language.
- Shugo adds `<link rel="alternate" hreflang="…">` to the head the same way it adds stylesheet links. A layout would have to read the current page URL to add those links, forcing a separate evaluation per page.
- Put `<html lang>` in the site shell, `src/site.html`. Shugo replaces `%shugo.lang%` with the page language and `%shugo.head%` with the head content. See [Layouts](../../spec/layouts.md).
- URLs use explicit language selection, following Google's guidance on browser-language redirects.

### Optional `[[lang]]` route parameter

SvelteKit can use an optional route parameter for a locale prefix. For example, `src/routes/[[lang]]/about/+page.svelte` serves both `/about` and `/es/about`. On the first route, `params.lang` is `undefined`. An optional parameter cannot follow a rest parameter, which consumes the rest of the path.

In Shugo, `src/pages/[[lang]]/about.svelte` could serve `/about` and `/<language>/about`. `getStaticPaths` would enumerate the values, omitting `lang` from the parameter object for the unprefixed path.

```svelte
<!-- src/pages/[[lang]]/about.svelte -->
<script module>
  export function getStaticPaths() {
    return [{ params: {} }, { params: { lang: "es" } }]
  }
</script>

<script>
  import { page } from "shugo"

  const locale = page.params.lang ?? "en"
</script>
```

- The routes `/about` and `/es/about` export to `about.html` and `es/about.html`.
- A page with two parameters enumerates the combinations. For `src/pages/[[lang]]/products/[slug].svelte`, return `{ params: { slug } }` for English and `{ params: { lang: "es", slug } }` for Spanish.
- The server returns 404 for any omitted path, such as `/de/about`.
- With both `src/pages/about.svelte` and `src/pages/[[lang]]/about.svelte`, the build reports a duplicate `/about`. For a prefixed path the usual precedence applies. Literal segments outrank parameters, and parameters outrank rest segments. See [Routing](../../spec/routing.md).
- The default language of the unprefixed path is `page.params.lang ?? "en"`.

Using `[[lang]]` treats the language as an ordinary route parameter. Every page must enumerate its own languages. The project must validate translations, create `alternates`, and write `hreflang` itself. A page that reads its language from another source can disagree with the URL.

With `i18n` settings, filenames stay the same and Shugo applies the prefixes. A general optional parameter, `[[name]]`, can be added separately when needed. Combining the dedicated configuration with a `[[lang]]` directory should produce a build error with a hint.

### Incremental updates

- Updating a translated string reevaluates only the pages that display it. Keeping the catalogs in the database also lets translators update the content without changing project source.
- Database reads using `where({ locale })` restrict the impact of a text change to its language.
- A component that reads neither the locale nor strings can remain shared across languages. A component importing `t` or `locale` becomes a separate shared block for each language because the locale is part of its key.
- With the same routes in each language, page count is the number of routes times the number of languages.

### Out of scope

- Separate per-language markup files such as `about.es.svelte`. If the page genuinely needs a different structure in Spanish, use a separate page with `export const locales = ["es"]`.
- ICU formatting, which adds a second syntax to validate inside JSON strings.
- One domain per language.

## Open questions

- Should a page template and JSON strings be shared across languages?
- Should the default language have a URL prefix? The proposal uses unprefixed URLs.
- Should plural messages use objects or ICU when integrated with translation services?
- Where should long-form content live? Articles and descriptions are expected to come from localized database rows.
- How should right-to-left languages set `dir` on `<html>` and use logical CSS properties?
- When should Shugo support the general `[[name]]` optional route parameter?
