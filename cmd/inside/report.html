Inside Shugo

This project goes through compilation, an initial build, and five data changes, each followed by an update. The report captures intermediate data from that run. This is the fifth trial, on the lab/inside branch.

To reproduce: go build -o bin/shugo ./cmd/shugo && go run ./cmd/inside examples/inside. The example project is examples/inside. To customize the data changes, edit examples/inside/data/steps.json.

Template program
A list of operations representing the template markup with placeholders for values. Each file has one, stored in _build/site.json and in the store.
File JS module
A function the compiler generates from the .shugofile. It runs the data code and writes each expression's value in order. The modules are bundled in _build/eval.mjs.
Block
One rendering of a template: a page, layout, component, or markup passed into a slot.
Value tape
The expression values for a block, in order. Identical tapes share one entry keyed by their content hash.
Record
All the blocks for a page or shared block. Each records its template, value tape, nested blocks, and slots.
Shared block
A component called with plain props. It is computed once for the site and stored by name. Pages reference it by number.
Reader
A page, shared block, or route page list that read project data.
Read shape
A table, the columns used to look up rows, and the columns whose changes matter. For example, a lookup on variants by product that tracks position, stock, and title.
Read
A read shape and its lookup values, such as variants where product = p1. A row affects a read if the row matches or previously matched those values and was inserted, deleted, or changed in a relevant column.
Journal
The _shugo_journal table in the project database records which rows changed and their earlier values.

2. Compilation: JS and template programs

For each .shugo file, the compiler produces two things. The JS module runs the data code and records each expression's value as it renders the template. Each call to $$.text, $$.attr, $$.branch, $$.loop/$$.count, $$.slot adds a value to the block's tape. Program represents the same markup, with each expression replaced by an operation that takes the next value from the tape. The compiler emits both in one pass, keeping them in the same order.

This JS comes from the built _build/eval.mjs ({{.Compiled.Bundle}} bytes). Imports have already been resolved, producing names like ProductCard_default.

4. First build: the Go and JS exchange

Go starts _build/eval.mjs and exchanges messages over two separate channels. Each message contains a length, a code, and a body. The body uses these separators: ␀ precedes each value on the tape, ␁ separates blocks in a record, ␂ separates fields, and ␃ separates records. The messages come from examples/inside/tap.sh, which records each side in order. The sequence across both sides is unavailable. While computing, JS can request an index (I) and wait for Go to reply.

8. Proposal: values inside records

Currently, a block's record contains the value tape's hash. The tape lives in its own row in value. To render a page, the server separately looks up its record, the records of any shared blocks, and their value tapes. Embedding the tapes in page and shared block records would reduce this to one lookup per record.
