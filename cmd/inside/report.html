Inside Shugo

This project goes through compilation, an initial build, and five data changes, each followed by an update. The report captures intermediate data from that run. This is the fifth trial, on the lab/inside branch.

To reproduce: go build -o bin/shugo ./cmd/shugo && go run ./cmd/inside examples/inside. The example project is examples/inside. To customize the data changes, edit examples/inside/data/steps.json.

Template skeleton
A list of operations representing the template markup with placeholders for values. Each file has one, stored in _build/site.json and in the store.
File JS module
A function the compiler generates from the .shugofile. It runs the data code and writes each expression's value in order. The modules are bundled in _build/eval.mjs.
Block
One rendering of a template: a page, layout, component, or snippet.
Value tape
The expression values for a block, in order, stored with the block in its record.
Record
All the blocks for a page or shared block. Each records its template, value tape, nested blocks, and caller-supplied snippets.
Shared block
A component called with plain props. It is computed once for the site and stored by name. Pages reference it by number.
Reader
A page, shared block, or route page list that read project data.
Read shape
A table, the columns used to look up rows, and the columns whose changes matter. For example, a lookup on variants by product that tracks position, stock, and title.
Read
A read shape and its lookup values, such as variants where product = p1. A row affects a read if the row matches or previously matched those values and was inserted, deleted, or changed in a relevant column.
Journal
The _shugo_journal table in the project database records which rows changed and their earlier values.

2. Compilation: JS and template skeletons

For each .shugo file, the compiler produces two things. The JS module runs the data code and records each expression's value as it renders the template. Each call to $$.text, $$.attr, $$.branch, $$.loop/$$.count, $$.render adds a value to the block's tape. Skeleton represents the same markup, with each expression replaced by an operation that takes the next value from the tape. The compiler emits both in one pass, keeping them in the same order.

This JS comes from the built _build/eval.mjs ({{.Compiled.Bundle}} bytes). Imports have already been resolved, producing names like ProductCard_default.

4. First build: Go requests and JS responses

Go decides what to compute. JS runs the project code and returns records. This division supports updates because Go tracks what changed and what the store already contains. The first build uses the same process, so it runs in several rounds.

  • Rounds by level. Go discovers a shared block when a record references it. A page renders a card, for example, or a layout renders a header. Go checks the store and requests any missing blocks in the next round. A first build starts with pages, then processes their shared blocks and any further dependencies.
  • Indexes on demand. The first time JS runs a query, it asks Go for an index and waits for a reply. Go alone writes to the database. The store remembers indexed queries, so Go tells JS at startup which indexes are ready.

gone — removed pages

A removed page retains the version in which it disappeared. Page and shared block records also store the version when they last changed. An update writes that version with the record. Export remembers its last version and rebuilds pages with newer records. It follows shows to find pages that render a newer shared block, directly or through another shared block. It deletes files for pages removed since the previous export. Version indexes support these lookups. A full rebuild clears the table and advances origin in meta. An export from an earlier version then writes every page.

Value tapes live inside the records, so each record needs one lookup. The transaction reads a single version of the store. An update that finishes during the transaction becomes visible to the next request.
