# Internationalization

A proposal on how the site is going to be assembled in multiple languages. Not yet. The proposal is made after studying Astro, SvelteKit with Paraglide, Next.js with next-intl, Nuxt i18n and Hugo; examples are written with Svelte templates, data are taken through `query` from the `shugo` module.

## Decisions

- 21 November 2026 year internationalization is put in the proposal.
- Translation strings are stored in the project database, not in code files: so changing a string only calculates the pages that show it (the proposal of the author of the project 22 November 2026 year, the advice is the same).

## What others do

| | One page file in all languages | Where do the lines come from | Default language address |
| --- | --- | --- | --- |
| Astro | no: Folder on the tongue | no catalogues, handwritten | without prefix |
| SvelteKit + Paraglide | yeah. | `messages/en.json`, function per line | configurable |
| Next.js + next-intl | yeah. | `messages/en.json`, ICU format | with prefix |
| Nuxt i18n | yeah. | files on the language, format vue-i18n | without prefix |
| Hugo | no: file or folder per language | `i18n/en.toml`, number shapes by CLDR | without prefix |

- Four out of five draw one pattern in all languages and read the strings by function. Astro, where the file is in the language, does not give line directories at all.
- The address is most often this: the default language without a prefix, the rest under `/<language>/`.
- The plural is different for everyone.
- The general trap is "current language" as a hidden state. With static assembly, there is no request from which to take it, and the language of one page can flow into another.

## Proposal

### Configuration

```json
{
  "site": "https://example.com",
  "data": "data/site.db",
  "i18n": {
    "locales": ["en", "es"],
    "default": "en",
    "prefixDefault": false
  }
}
```

English uses `/about` and Spanish uses `/es/about`. Export writes `about.html` and `es/about.html`. The home pages become `index.html` and `es.html`.

### One page in all languages, language is a clear value

Each page file is calculated once per language. The language is not a hidden state, but the value of `locale` from the `shugo` module. `getStaticPaths` is called for each language separately and takes the language there: each language has its own addresses.

The texts of the goods in different languages are in the database of a separate table with a column of language:

```svelte
<!-- src/pages/products/[slug].svelte -->
<script module>
  import { query, page, t, locale } from "shugo"

  export function getStaticPaths() {
    return query("product_texts").select("slug", "product").where({ locale }).all()
      .map(({ slug, product }) => ({ params: { slug }, key: product }))
  }
</script>

<script>
  const text = query("product_texts").where({ locale, slug: page.params.slug }).first()
  const product = query("products").get(text.product)
  const date = new Intl.DateTimeFormat(locale, { timeZone: "America/New_York" })
</script>

<svelte:head><title>{text.title}</title></svelte:head>
<h1>{text.title}</h1>
<p>{t("product.inStock", { count: product.stock })}</p>
<time datetime={product.arrival}>{date.format(new Date(product.arrival))}</time>
```

- `key` associates localized versions of a page. Shugo links `/products/pitcher` and `/es/products/jarra` as the same page.
- `where({ locale })` is an equality lookup. Changing the Spanish text affects only pages that read that row.
- A page that is not in any language says this in `<script module>`: `export const locales = ["en"]`.

### Lines

The lines are in the table of the project database: key, language, text. Write them conveniently with JSON files - one per language; they are transferred to the [data Adapter](data-adapter.md) table or simple download, like any other data:

```json
// locales/es.json — source of lines, not project code
{
  "nav.home": "Home",
  "product.inStock": {
    "one": "{count} item in stock",
    "other": "{count} items in stock"
  }
}
```

- The keys are flat, substitutions in braces.
- A plural message is an object keyed by CLDR category. Shugo selects the category from `count`. English uses `one` and `other`. Include the count in the message.
- `t("key", { … })` from the module `shugo` reads a string of the language of this page from the table of lines through `query`, so the page remembers which lines it read. In the component also:

```svelte
<!-- src/components/Stock.svelte -->
<script>
  import { t } from "shugo"

  let { count } = $props()
</script>

<p>{t("product.inStock", { count })}</p>
```

### What is checked during assembly

The assembly stops if:

- the key is not in the default language;
- in the line of another language, there are no substitutions;
- in the object of plural there is no form that this language needs;
- the key is not a string written in code, but is calculated.

If the key is not in another language, the default language string is taken, and a list of such keys appears in the report.

### What framework gives itself

- `alternates` from the module `shugo` — the same page in other languages: `[{ locale, url }]`. It makes a language switch:

  ```svelte
  <!-- src/components/LanguageSwitch.svelte -->
  <script>
    import { alternates } from "shugo"
  </script>

  <nav>
    {#each alternates as other}
      <a href={other.url} hreflang={other.locale} lang={other.locale}>{other.locale}</a>
    {/each}
  </nav>
  ```

- `localeUrl("/about", "es")` from the `shugo` module is the page address in another language.
- `<link rel="alternate" hreflang="…">` tags Shugo adds to `<head>` itself as a link to styles. If they were written by a layout, it would read the page address and be calculated on each page rather than once.
- `<html lang>` is written not in the layout, but in the shell of `src/site.html`, one for the entire site ([Layouts](../../spec/layouts.md)). The language of the page Shugo puts there itself, in place of `%shugo.lang%`, as head — in place of `%shugo.head%`. The layout to read the language for the sake of `lang` is not necessary.
- There are no redirects to the browser language: Google advises not to do them.

### Optional address parameter `[[lang]]`

So the language in the address is done in SvelteKit, if you do not take a library like Paraglide. Below is what it is, what it would look like in Shugo and why settings are offered for languages.

**What's that?** Option in double square brackets may be missing. In SvelteKit, the `src/routes/[[lang]]/about/+page.svelte` file responds to both `/about` and `/es/about`; in the first case, `params.lang` is `undefined`. An optional parameter cannot stand immediately after the remainder of the path (`[...path]/[[lang]]`): the remainder takes everything, and the parameter would have nothing to take.

**As in Shugo.** The `src/pages/[[lang]]/about.svelte` file gives the addresses `/about` and `/<language>/about`. As with any parameter, its values list `getStaticPaths`; the absence of a parameter is recorded by the fact that it is not in `params`:

```svelte
<!-- src/pages/[[lang]]/about.svelte -->
<script module>
  export function getStaticPaths() {
    return [{ params: {} }, { params: { lang: "es" } }]
  }
</script>

<script>
  import { page } from "shugo"

  const locale = page.params.lang ?? "en"
</script>
```

- `/about` and `/es/about` are obtained, while exports include `about.html` and `es/about.html`.
- A page with another parameter enumerates all combinations. For `src/pages/[[lang]]/products/[slug].svelte`, return `{ params: { slug } }` for English and `{ params: { lang: "es", slug } }` for Spanish.
- There are only listed addresses: `/de/about` no one has listed this is 404.
- `src/pages/about.svelte` next to `src/pages/[[lang]]/about.svelte` give one `/about` address — build error, as for any two pages with one address. Where the parameter is present, it obeys the general rule: text is stronger than the parameter, the parameter is stronger than the path remainder ([Routing](../../spec/routing.md)).
- The main language without a prefix is the address without the parameter: `page.params.lang ?? "en"`.

**It's worse than settings.** With `[[lang]]`, the language is a normal address parameter, and Shugo knows nothing about languages:

- every page, even a simple “About us”, you need a folder `[[lang]]` and `getStaticPaths` with a list of languages more code and more places where the agent can forget the language;
- Shugo can not check the transfers, give `alternates` and `hreflang` tags - all this is written by the project;
- language is easy to start taking not from the address, but from somewhere else, and the pages will diverge.

With `i18n` settings, file paths remain the same as for a single language, and the prefix adds Shugo.

**What is proposed.** Languages are through settings. `[[name]]` is a generic optional parameter, as in SvelteKit, separate from languages when there is a case for it. In a project with `i18n` settings, the `[[lang]]` folder is an error with a hint: two ways to do the same thing.

### Incremental updates

- Lines are data, not code. Changed one line - only the pages where it is shown are calculated. If the lines were in `src/` and imported, they would be part of the project code, and changing any line would compute the entire site. Translators then rule the lines as data.
- Texts in different languages taken from the database by `where({ locale })` are read exactly: changing text in one language affects only pages of this language.
- A component that does not read a language or a string remains a common block in all languages. A component that imports `t` or `locale` from the `shugo` module becomes a common block in the language: the language enters its name as a parameter.
- Pages are multiplied by the number of languages in one language.

### What is not in the offer

- Language file (`about.es.svelte`). The markup is split between copies, and each structure change is a revision in several places. If the page in another language is arranged differently, this is a separate file with `export const locales = ["es"]`.
- ICU format. It is more expressive, but it is the second syntax inside the lines of JSON, and it is harder to check it when assembling.
- Domain on the tongue.

## Open questions

- Do you agree with the “one page per language and line approach in JSON”?
- Default language prefix. Tip: No prefix.
- Line format: An object with number forms like here, or ICU if the lines are going to go into translation services.
- Where long texts live: articles and descriptions come from the database in their own language, not from line directories.
- Letter from right to left: `dir` on `<html>` and logical properties of CSS.
- `[[name]]` as a general optional address parameter: do now or when you need to.
